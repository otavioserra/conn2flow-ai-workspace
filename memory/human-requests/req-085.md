## 📋 Escopo do Lote (`BATCH-087`)

### 1. `c2f-documentation` (`.gemini/skills/c2f-documentation/SKILL.md` + tradução EN)
- Na seção de publicação (`docs:build`), documentar o padrão **"Build a partir de `git archive origin/main` (publicar só o que está commitado)"**:
  1. Antes de gerar `/docs/` a partir de um repositório Core com árvore compartilhada ou alterações em andamento, extrair uma fonte limpa diretamente do commit aprovado (`git fetch origin` + `git archive origin/main -- ai-workspace/ | tar -x -C <dir-temporario>` ou equivalente determinístico).
  2. Executar `docs:build` contra a fonte limpa extraída (ou garantir que a fonte corresponda exatamente ao commit de `origin/main`, sem rascunhos nem arquivos não rastreados do working tree).
  3. Remover o diretório temporário ao final e nunca publicar documentação não commitada/integrada em `origin/main`.

### 2. `c2f-json-resources-sync` (`.gemini/skills/c2f-json-resources-sync/SKILL.md` + tradução EN)
- Adicionar a regra **"Merge atômico: partes e manifest do mesmo lado"** (complementando a seção de commit seletivo da `REQ-084`):
  1. Ao resolver conflitos de merge que afetam recursos (`pages.json`, `components.json`, `layouts.json`, `templates.json` e seus arquivos físicos em `resources/<idioma>/...`), **os arquivos físicos (HTML/CSS/MD) e a entrada correspondente no manifest devem vir do mesmo lado** (`ours` ou `theirs`).
  2. É proibido misturar o corpo físico de um lado com metadados/versão/checksum do outro lado.
  3. Se for necessário combinar alterações de ambos os lados num mesmo recurso, mesclar conscientemente o conteúdo, **limpar os checksums afetados** no manifest e deixar o pipeline oficial recalcular (`atualizacao-dados-recursos.php`), validando JSON e diff antes do commit.

### 3. `c2f-project-pipeline-and-tasks` (`.gemini/skills/c2f-project-pipeline-and-tasks/SKILL.md` + tradução EN)
- Adicionar o padrão **"Branch local de integração com conferência de hash"** (complementando a Regra #10 / `REQ-077`):
  1. Quando precisar consolidar ou validar entregas sem misturar alterações da árvore de trabalho, criar/atualizar uma branch local de integração a partir da base remota verificada (`git fetch origin`).
  2. Registrar e conferir explicitamente os hashes (`git rev-parse HEAD`, `git rev-parse origin/main` e o hash do commit aprovado) **antes e depois** da integração.
  3. Só prosseguir para `git push` ou pipeline de deploy após confirmar que o `HEAD` da integração corresponde exatamente ao hash esperado, sem commits estranhos nem alterações sujas fora do escopo.

### 4. `c2f-shell-and-windows-traps` (`.gemini/skills/c2f-shell-and-windows-traps/SKILL.md` + tradução EN)
- Adicionar uma nova armadilha numerada **"Como reconhecer um `index.lock` órfão no Windows"**:
  1. **Sintoma**: `fatal: Unable to create '.../.git/index.lock': File exists` (ou `.git/worktrees/<nome>/index.lock`) após comando Git interrompido, timeout ou travamento no Windows/OneDrive.
  2. **Proibição**: nunca apagar `index.lock` sem antes verificar se existe processo `git.exe` ativo operando no repositório (apagar lock ativo corrompe o índice).
  3. **Diagnóstico obrigatório (PowerShell)**:
     - Verificar processos `git.exe` ativos e seus argumentos (`Get-CimInstance Win32_Process -Filter "Name='git.exe'" | Select-Object ProcessId, CreationDate, CommandLine`).
     - Inspecionar o arquivo de lock (`Get-Item -LiteralPath .git/index.lock | Select-Object FullName, Length, LastWriteTime`) e confirmar que o timestamp não está mudando.
  4. **Ação segura**:
     - Se houver `git.exe` ativo atuando naquele repo/worktree: **aguardar**, nunca apagar lock alheio.
     - Se **nenhum** `git.exe` estiver atuando naquele repo/worktree e o arquivo estiver parado (órfão): remover apenas o arquivo literal (`Remove-Item -LiteralPath .git/index.lock`) e conferir integridade com `git status --short` (e `git fsck` se houve interrupção durante gravação).
