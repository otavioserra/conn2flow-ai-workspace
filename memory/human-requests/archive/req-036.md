## Objetivo

Reestruturar a interface e a camada de execução da extensão Conn2Flow Dev Tools para reduzir duplicidade, proteger ações de impacto, incluir a infraestrutura de backlog SDD, oferecer operações guiadas de release do **Gestor** e do **Gestor Instalador** e disponibilizar a interface em português e inglês.

Esta requisição foi aprovada pelo Humano-no-Loop em 2026-08-29. A aprovação autoriza a implementação supervisionada, mas não autoriza commit, push, deploy ou release real.

## Achados da revisão do código atual

### Prioridade crítica

1. `AgentBridgeManager.notifyArchitect()` monta uma sequência que adiciona diretórios SDD inteiros, cria commit e envia diretamente para `main`, sem respeitar o modo supervisionado e sem confirmação final.
2. O prompt de `launchClaudeGoal()` instrui o executor a sincronizar o Git ao final, mesmo quando a sessão está supervisionada.
3. Ações personalizadas de `.c2f/actions.json` podem executar comandos arbitrários sem uma barreira explícita de `workspace.isTrusted`.
4. Os scripts canônicos de release do Gestor e do Instalador usam `git add .`, proibido pela governança e capaz de incluir alterações alheias ao release.
5. Deploys e outras ações de alto impacto podem ser enviados ao terminal sem confirmação clara do alvo e sem comprovação do código de saída.

### Prioridade alta

1. A árvore possui muitas ações simultâneas, seções expandidas e comandos duplicados entre **Manager & Core** e **Projetos & Environment**.
2. O alvo de projeto possui fallback implícito para `conn2flow-site`, mesmo quando nenhum ambiente foi detectado.
3. Há caminhos pessoais e proprietário GitHub fixos no runtime, reduzindo a portabilidade da extensão.
4. O terminal reutilizável pode receber comandos dentro de um terminal não gerenciado ou com diretório inadequado.
5. Mensagens de sucesso podem ser exibidas quando o comando apenas foi enviado ao terminal, antes de seu término real.
6. Preferências de visualização, escopo SDD, alvo, modo de terminal e Auto-Gardening não são plenamente persistidas.
7. O Auto-Gardening anuncia automação, mas atualmente não implementa integralmente o comportamento sugerido pelo nome.
8. Alguns atalhos de documentação apontam para arquivos de assunto diferente do rótulo exibido.
9. A extensão é ativada de modo amplo, inclusive fora de um workspace Conn2Flow.
10. Rótulos, tooltips, prompts e mensagens estão majoritariamente fixos em português, sem catálogo de localização ou seleção de idioma.

## Estrutura de interface proposta

Organizar a árvore em grupos progressivos, com seções secundárias recolhidas por padrão e estado persistido:

1. **Visão Geral**: repositório, branch, alvo, autonomia, saúde do ambiente e ações recomendadas.
2. **SDD & Planejamento**: requisição atual, lotes, validação, **Backlog**, decisões, handoff e gardening.
3. **Core & Releases**: atualização do Gestor, release do Gestor, release do Gestor Instalador e operações do Instalador.
4. **Projetos & Test Environment**: alvo explicitamente selecionado, atualização, sincronização e deploy contextualizados.
5. **Ambiente & Diagnóstico**: Docker, logs, testes, serviços e auditorias.
6. **Agentes, Documentação & Configurações**: pontes supervisionadas, guias coerentes e preferências persistidas.

## Interface multilanguage

Implementar inicialmente **Português do Brasil (`pt-BR`)** e **Inglês (`en`)**, aproveitando o suporte nativo do VS Code:

- o modo padrão deve ser **Automático**, resolvido por `vscode.env.language`;
- idiomas do VS Code como `pt`, `pt-BR` e variantes compatíveis devem resolver para `pt-BR`;
- `en`, variantes de inglês e qualquer idioma ainda não suportado devem usar inglês como fallback;
- adicionar ao painel e às configurações a opção **Idioma da Extensão: Automático / Português (Brasil) / English**;
- persistir a escolha explícita em `conn2flow.language`, com escopo de usuário e possibilidade de sobrescrita por workspace;
- atualizar imediatamente árvore, prompts, mensagens e tooltips após a troca; contribuições estáticas que dependam do manifesto podem solicitar Reload Window;
- usar `package.nls.json` e `package.nls.pt-br.json` para títulos e comandos declarados no manifesto;
- centralizar strings de runtime em catálogos tipados e impedir novos textos literais fora da camada de localização;
- manter uma fonte canônica de chaves e gerar/validar os artefatos derivados para evitar divergência entre manifesto e runtime;
- aceitar `CONN2FLOW_LANGUAGE=pt-BR|en` apenas como fallback opcional para desenvolvimento, testes automatizados ou execução sem preferência persistida; a detecção nativa do VS Code continua prioritária no modo Automático;
- ao criar ou instalar templates de agentes, propagar explicitamente a linguagem selecionada para os instaladores já existentes (`--language pt-br|en` ou equivalente PowerShell), sem alterar arquivos `.env` do projeto silenciosamente.

### Precedência de idioma

1. escolha explícita `conn2flow.language = pt-BR|en`;
2. em `auto`, idioma da interface obtido de `vscode.env.language`;
3. fallback opcional `CONN2FLOW_LANGUAGE`, somente quando o idioma automático não for suportado;
4. inglês como fallback final.

A preferência da extensão não deve mudar o idioma global do VS Code nem misturar-se com idioma de conteúdo ou tenant do Gestor.

## Navegação de backlog

Adicionar ao menu SDD um navegador de `sdd/backlog/` com estas regras:

- usar `BACKLOG-INDEX.md` como índice de exibição;
- mostrar identificador, tipo e status (`ICEBOX`, `IN-DISCUSSION`, `READY`, `COMPLETED` etc.);
- permitir filtros por status e abertura do item original;
- sinalizar divergência entre o status do índice e o arquivo individual;
- respeitar o **Intake Gate**: backlog nunca vira execução automaticamente;
- oferecer, quando aplicável, **Promover para Requisição**, sempre por ação humana explícita e fluxo SDD governado.

## Formulários compostos para ações multiparâmetro

A API nativa de `InputBox`/`QuickPick` do VS Code não oferece vários campos de texto editáveis no mesmo modal. Para evitar sequências longas de prompts, implementar um formulário reutilizável em `WebviewPanel` para ações que exigem múltiplos parâmetros.

Requisitos do componente:

- receber schema declarativo de campos (`text`, `textarea`, `select`, `checkbox`, somente leitura);
- apresentar todos os parâmetros em uma única tela compacta;
- validar campos obrigatórios e valores permitidos antes do envio;
- exibir resumo do impacto, alvo e comando resultante;
- aplicar Content Security Policy com nonce, escaping de conteúdo e nenhum recurso remoto;
- devolver os valores somente ao comando que abriu o formulário;
- permitir cancelamento sem efeito colateral;
- possuir textos `pt-BR`/`en` e navegação acessível por teclado;
- ser usado inicialmente pelos releases do Gestor e do Gestor Instalador;
- ficar disponível para cadastro/scaffold de projetos e outras ações multiparâmetro em evoluções do mesmo painel.

### Política de apresentação por ação

Cada ação deve declarar `presentation: auto | quick | form`, com `auto` seguindo estas regras:

- nenhum parâmetro: execução direta, mantendo as confirmações exigidas pelo impacto;
- um parâmetro: `InputBox` ou `QuickPick` nativo;
- dois parâmetros: fluxo nativo quando o segundo depender do primeiro; formulário quando forem independentes;
- três ou mais campos: formulário composto automaticamente;
- release, deploy remoto ou ação destrutiva: formulário com resumo final obrigatório, independentemente da quantidade de campos;
- `quick` e `form` permitem sobrescrita explícita quando a experiência específica da ação justificar.

O WebviewPanel é um painel interno do VS Code, não uma janela modal nativa do sistema operacional.

## Central de releases do Core

### Fontes canônicas confirmadas

- Gestor: `.github/workflows/release-gestor.yml`, tags `gestor-v*` e comando `c2f manager:release`.
- Gestor Instalador: `.github/workflows/release-instalador.yml`, tags `instalador-v*` e comando `c2f installer:release`.
- A extensão deve chamar os comandos oficiais do `c2f`, sem duplicar versionamento ou publicação.

### Operações da interface

Em **Core & Releases**, disponibilizar duas operações independentes:

- **Criar Release do Gestor**;
- **Criar Release do Gestor Instalador**.

Cada operação deve abrir um assistente que:

1. execute preflight de repositório, branch, remoto, autenticação e permissão;
2. exija árvore Git limpa antes do início;
3. apresente versão atual, incremento (`patch`, `minor`, `major`), próxima versão e tag exata;
4. solicite mensagem da tag e mensagem do commit;
5. permita o modo oficial suportado (`automatic` ou `manual`), explicando a diferença;
6. mostre o comando e o workflow afetado antes da confirmação;
7. exija confirmação modal final;
8. acompanhe o término real e apresente sucesso somente após código de saída válido;
9. ofereça acesso ao workflow/release resultante.

### Permissões e visibilidade

- validar autenticação com `gh auth status`;
- consultar `viewerPermission` do repositório remoto;
- considerar `WRITE`, `MAINTAIN` ou `ADMIN` como permissão para release;
- ocultar criação de release para `READ` ou `TRIAGE`;
- se a permissão não puder ser determinada, mostrar somente **Verificar permissão de release**;
- exigir também Core correto, branch não destacada, remoto compatível, ausência de colisão de tag e nenhum release concorrente.

### Endurecimento obrigatório dos scripts

Antes de expor os botões de release:

- remover `git add .` dos scripts do Gestor e do Gestor Instalador;
- abortar se já houver alterações não relacionadas ao release;
- adicionar explicitamente somente arquivos gerados ou alterados pelo processo;
- preservar o acionamento dos workflows por `gestor-v*` e `instalador-v*`;
- testar árvore suja, permissão insuficiente, tag existente, push rejeitado e workflow com falha.

## Camada única e segura de execução

Criar um executor de comandos usado por toda a extensão:

- terminal dedicado Conn2Flow e diretório de trabalho explícito;
- bloqueio de comandos customizados em workspace não confiável;
- classificação de impacto (`local`, `mutating`, `remote`, `destructive`);
- confirmação proporcional ao impacto;
- captura de código de saída e logs;
- mensagem de sucesso somente após conclusão comprovada;
- serialização de pipelines incompatíveis;
- cancelamento e estado visual de operação em andamento;
- remoção de caminhos absolutos e identidades GitHub fixas.

## Critérios de aceite

- [ ] Nenhuma ponte de agente executa commit ou push sem ação humana explícita.
- [ ] Nenhum script de release usa `git add .` ou `git add -A`.
- [ ] Ações customizadas são bloqueadas em workspace não confiável.
- [ ] A árvore apresenta hierarquia mais curta, contextual e persistente.
- [ ] A extensão acompanha automaticamente o idioma do VS Code em português e inglês.
- [ ] O painel permite sobrescrever o idioma com `Português (Brasil)` ou `English`.
- [ ] Manifesto, árvore, prompts, mensagens e tooltips possuem paridade de tradução validada.
- [ ] A linguagem selecionada é propagada aos instaladores bilíngues de templates.
- [ ] O backlog pode ser consultado e filtrado sem burlar o Intake Gate.
- [ ] Divergências de status do backlog são sinalizadas.
- [ ] Gestor e Gestor Instalador possuem assistentes de release independentes.
- [ ] Os parâmetros de release são preenchidos em um único formulário composto, sem sequência de InputBox/QuickPick.
- [ ] Ações de release ficam ocultas para usuários sem permissão conhecida.
- [ ] Permissão indeterminada oferece apenas diagnóstico seguro.
- [ ] Cada release usa o comando `c2f` e o workflow canônico correspondente.
- [ ] Árvore suja, tag existente, branch destacada ou push sem permissão bloqueiam o release.
- [ ] A interface só anuncia sucesso depois da conclusão efetiva do comando.
- [ ] Deploys e releases exibem alvo e pedem confirmação explícita.
- [ ] Não existem caminhos pessoais ou proprietário GitHub fixos no runtime.
- [ ] Testes automatizados, compilação e VSIX passam sem regressão.
