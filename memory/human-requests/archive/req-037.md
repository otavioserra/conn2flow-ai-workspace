## Objetivo

1. **Reconciliar e Estabilizar o Runtime da Extensão VS Code**:
   - Reverter qualquer regressão acidental em `vscode-extension/src/extension.ts` preservando o conjunto completo de 51 comandos, Workspace Trust, modos de visualização, localização bilíngue e gerenciadores (`LocalizationManager`, `BacklogManager`, `ReleaseManager`).
   - Eliminar o acúmulo e encadeamento visual de abas de código-fonte Markdown ao navegar no modo "Preview (Apenas Renderizado)", garantindo foco imediato e exclusivo na aba de Preview renderizada (Custom Editor MPE ou fallback nativo).

2. **Fluxo de Release Inteligente em Duas Fases**:
   - Separar o release em **Fase 1: Preparar Release (Diagnóstico & Pré-Geração)** e **Fase 2: Executar Release (Gatilho Final)**.
   - A Fase 1 deve abrir mesmo com árvore de trabalho suja, exibindo diagnóstico completo: arquivos modificados, permissão GitHub, branch atual, conflito de tags e rascunho de notas de versão / commit messages geradas via Conventional Commits.
   - O rascunho deve ser mantido em `workspaceState` da extensão (sem sujar o repositório).
   - A Fase 2 (Execução do Release) permanece rigorosamente desabilitada e travada até que o repositório esteja limpo e validado.

3. **Automação Mandatória de Documentação Bilíngue Pré-Release**:
   - Integrar ao pipeline de preparação e execução do release a sincronização e atualização prévia das documentações:
     * `README.md` (Inglês) e `README-PT-BR.md` (Português) com as novas versões e notas consolidadas.
     * Changelogs oficiais (`CHANGELOG.md`).
     * Cabeçalho e corpo dos workflows GitHub Actions (`.github/workflows/*.yml`).
   - Aplicar estritamente a skill `c2f-documentation-governance` e `c2f-multilingual-system`, impedindo release com documentações desatualizadas.

## Escopo Detalhado

### 1. Foco e Ciclo de Vida do Preview Markdown
- Em modo `preview`:
  * Ao solicitar a abertura de um documento Markdown (`openMarkdownFile`), qualquer aba de texto bruta aberta pelo VS Code em segundo plano para renderizar o documento deve ser fechada imediatamente.
  * O preview correspondente ao arquivo atual deve receber foco ativo.
  * Ao alternar entre documentos (ex: de um guia para uma requisição ou outro manual), fechar a aba de preview anterior gerenciada, evitando acúmulo de abas na barra de editores.
  * Preservar abas de arquivos abertos manualmente pelo usuário que não pertençam ao ciclo de preview da extensão.

### 2. Painel e Lógica de Release (Duas Fases)
- **Fase 1: Diagnóstico e Preparação**:
  * Disponível a qualquer momento pelo menu da árvore.
  * Exibe lista de arquivos modificados sem bloquear o acesso ao painel de preparação.
  * Permite sugerir e editar mensagens de commit e tags baseadas no histórico recente de commits e no batch ativo.
  * Ação rápida para "Abrir Controle de Código-Fonte" (`workbench.view.scm`) para que o desenvolvedor possa revisar ou commitar pendências.
- **Fase 2: Trava de Execução**:
  * Botão de "Executar Release" fica ativo apenas quando `git status --porcelain` retornar vazio e as permissões forem confirmadas.
  * Etapa pré-release executa ou exige a atualização dos arquivos de documentação (`README.md`, `README-PT-BR.md`, `CHANGELOG.md`, `.github/workflows/`).

### 3. Validação e Testes
- Adicionar/atualizar testes unitários em `vscode-extension/test/`:
  * `markdownPreviewPolicy.test.cjs`: garantir que o fechamento e foco de abas respeitam as regras sem fechar arquivos alheios.
  * `releasePolicy.test.cjs`: cobrir a separação de fases, validação de documentação e geração de rascunhos sem dirty tree block na fase 1.
- Executar compilação TypeScript (`npm run compile`), suíte de testes (`npm test`) e verificação de integridade do VSIX local.
