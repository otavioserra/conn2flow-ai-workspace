## Objetivo

Corrigir a seleção da execução do workflow do GitHub Actions no método `findWorkflowRun` em `vscode-extension/src/providers/releaseManager.ts`, garantindo que o `gh run watch` monitore a execução correta, recente e ativa em vez de capturar execuções antigas ou falhas passadas para a mesma tag.

---

## Diagnóstico do Problema

1. **Bug em `findWorkflowRun()`**:
   * O método consulta `gh run list --workflow <workflow> --json databaseId,headBranch --limit 20` e busca o primeiro item com `item.headBranch === tag`.
   * Quando uma execução anterior para a mesma tag já existiu (por exemplo, após uma tentativa que falhou ou um re-disparo), a API do GitHub Actions pode listar primeiro a execução antiga já concluída com `failure`.
   * O método não filtrava por `status` (`in_progress`, `queued`) nem ordenava por `createdAt` em relação ao momento do disparo local.
   * Resultado: O comando executava `gh run watch <run-antiga-com-falha> --exit-status`, retornando imediatamente erro no terminal e abortando a limpeza do rascunho de release e a notificação de sucesso, mesmo que a nova run estivesse rodando (e inclusive concluísse com sucesso no GitHub).

2. **Limpeza do Rascunho no Sucesso**:
   * Como `workflow.succeeded` retornava falso devido ao watch na run errada, `workspaceState.update(this.draftKey(product), undefined)` não era chamado.
   * O rascunho ficava preso, mantendo a sensação de que o release não havia sido concluído.

---

## Escopo Detalhado

### 1. `vscode-extension/src/providers/releaseManager.ts`
- Modificar o método `findWorkflowRun(root: string, workflow: string, tag: string, triggeredAfter?: Date)`:
  * Incluir campos `status`, `conclusion` e `createdAt` na chamada `gh run list` (`--json databaseId,headBranch,status,conclusion,createdAt`).
  * Filtrar runs correspondentes à `headBranch === tag`.
  * Priorizar runs ativas (`status === 'in_progress' || status === 'queued'`) ou runs criadas a partir do momento do push (`createdAt >= triggeredAfter`).
  * Se a run encontrada já estiver finalizada com sucesso (`status === 'completed' && conclusion === 'success'`), aceitá-la imediatamente sem necessidade de watch.
  * Se houver apenas uma run antiga com falha anterior ao disparo, ignorá-la e aguardar nas tentativas (`attempts`) subsequentes até que o GitHub Actions registre a nova run.
- No método `execute()`:
  * Registrar o timestamp antes de executar o push (`const triggeredAfter = new Date()`).
  * Passar esse timestamp para `findWorkflowRun`.
  * Garantir tratamento robusto caso o workflow conclua com sucesso: limpar rascunho, resetar gates e atualizar a árvore.

### 2. Testes Automatizados (`test/releasePolicy.test.cjs` ou novo teste dedicado)
- Adicionar teste unitário cobrindo a lógica de desempate e seleção de workflow run (descartando runs obsoletas com falha e priorizando a mais recente ou ativa).
- Rodar suíte de testes completa (`npm test`).
- Gerar pacote VSIX compilado e reinstalar localmente com `--force`.
