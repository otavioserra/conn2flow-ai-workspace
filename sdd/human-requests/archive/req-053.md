## 1. Justificativa e Diagnóstico Técnico

Durante os testes de homologação do lote BATCH-054 e publicação de release, foram consolidados os seguintes requisitos:

1. **Permissão Negada na Leitura de Logs da VM (`Permission denied`)**:
   - O comando gerado por `vmDiagnosticsPolicy.ts` executa `ssh otavio@lab.conn2flow.local "tail -n 100 -- '/home/admin/.../logs/php-error.log'"`.
   - O arquivo `php-error.log` possui permissões `640` (`-rw-r-----`) pertencente a `admin:admin`, e `nginx-error.log` aponta para `/var/log/nginx/` (restrito ao root/adm).
   - Como a sessão SSH entra como usuário `otavio` (que possui privilégio de sudo sem senha configurado via `ssh_sudo: true`), o comando de leitura precisa invocar `sudo tail -n 100` para conseguir ler os arquivos sem erro de permissão.

2. **Execução Remota do Step 6/8 em Modo Duplo (CLI Primário + Fallback PHP)**:
   - Para instalações completas / gestores principais (`conn2flow-site`), o CLI `c2f` e a pasta `cli/` devem ser sincronizados para a instalação remota através do pipeline de Core (`sync-core-to-project.sh`), permitindo execução de comandos nativos `c2f`.
   - No `CssRebuildCommand.php`: implementar execução inteligente com **duplo modo**:
     * **Modo Primário**: se o binário `./c2f` ou `c2f` existir no destino remoto, executa via CLI (`./c2f css:rebuild`).
     * **Modo Fallback**: para tenants ou instalações que não possuam o CLI implantado, executa diretamente `php controladores/agents/arquitetura/css-regenerar.php --gestor=.`.

3. **Resolução de Tailwind e NODE_PATH no Gestor Remoto**:
   - No ambiente do Gestor remoto, o `tailwind-recursos.php` precisa resolver o executável global do Tailwind (`tailwindcss`) ou respeitar `NODE_PATH` (como `/opt/node-v22.22.3-linux-x64/lib/node_modules`) para resolver `@import "tailwindcss/utilities.css"` sem abortar quando não houver `node_modules` local.

4. **Portabilidade do Teste Unitário na Release do GitHub Actions**:
   - O teste `tests/Unit/PHP/ProjectSshPublicPathReq050Test.php` falhou no runner Ubuntu do GitHub Actions durante o workflow de release (`release.yml`), porque `escapeshellarg()` no Linux escapa aspas internas como `'\''`, enquanto no Windows usa aspas duplas `"..."`. As asserções devem suportar ambas as plataformas.

5. **Padronização do Host SSH para `lab.conn2flow.local`**:
   - Substituição oficial de referências ao IP `192.168.1.108` pelo hostname com SSL `lab.conn2flow.local` no `environment.json`, extensão e documentações de desenvolvimento.

## 2. Escopo Técnico da Entrega

- Em `src/vmDiagnosticsPolicy.ts`:

    ```typescript
    return `ssh -o BatchMode=yes -o ConnectTimeout=15 -p ${normalized.port} "${normalized.user}@${normalized.host}" "sudo tail -n 100 -- '${remoteLog}'"`;
    ```

### 2.2 Core CLI e Scripts (`conn2flow`):
- Em `ai-workspace/en/scripts/projects/sync-core-to-project.sh`:
  * Incluir a sincronização do arquivo executável `c2f` e do diretório `cli/` para o destino do projeto quando for projeto mestre/completo (`deploy_mode: "ssh"` ou com flag/configuração correspondente), garantindo que o CLI fique disponível na raiz da instalação remota.
- Em `cli/src/Commands/CssRebuildCommand.php`:
  * Em `regenerarViaSsh()`: implementar verificação de presença do CLI remoto. Se disponível, executa via CLI; caso contrário, executa o fallback chamando `php controladores/agents/arquitetura/css-regenerar.php --gestor=.`.
- Em `gestor/controladores/agents/arquitetura/tailwind-recursos.php`:
  * Em `tailwind_recursos_resolver_command()`: caso `$localCandidates` esteja vazio, verificar se existe o binário `tailwindcss` acessível no `PATH` do sistema antes de falhar.
- Em `tests/Unit/PHP/ProjectSshPublicPathReq050Test.php`:
  * Corrigir as 4 asserções de comandos SSH para serem portáveis entre Windows e Linux (`escapeshellarg`), garantindo que o CI do GitHub Actions passe 100% verde.
- Em `dev-environment/data/environment.json`:
  * Garantir que os projetos `snapphoton-local` e `conn2flow-site-local` usem `"ssh_host": "lab.conn2flow.local"`.
