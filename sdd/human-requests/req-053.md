## 1. Justificativa e Diagnóstico Técnico

Durante os testes de homologação do lote BATCH-054 nos projetos VM (HestiaCP), foram identificados 3 comportamentos a corrigir:

1. **Permissão Negada na Leitura de Logs da VM (`Permission denied`)**:
   - O comando gerado por `vmDiagnosticsPolicy.ts` executa `ssh otavio@192.168.1.108 "tail -n 100 -- '/home/admin/.../logs/php-error.log'"`.
   - O arquivo `php-error.log` possui permissões `640` (`-rw-r-----`) pertencente a `admin:admin`, e `nginx-error.log` aponta para `/var/log/nginx/` (restrito ao root/adm).
   - Como a sessão SSH entra como usuário `otavio` (que possui privilégio de sudo sem senha configurado via `ssh_sudo: true`), o comando de leitura precisa invocar `sudo tail -n 100` para conseguir ler os arquivos sem erro de permissão.

2. **Falha no Step 6/8 (`sudo: ./c2f: command not found`)**:
   - No `CssRebuildCommand.php`, o método `regenerarViaSsh()` tenta executar `./c2f css:rebuild` na pasta remota do Gestor.
   - Instalações do Gestor em servidores web não contêm o script `./c2f` ou o diretório `cli/` do repositório Core; elas contêm o script canônico `controladores/agents/arquitetura/css-regenerar.php` (da mesma forma que o `css:audit` invoca com sucesso `controladores/agents/arquitetura/css-auditoria.php`).
   - O `CssRebuildCommand.php` deve disparar via SSH diretamente `php controladores/agents/arquitetura/css-regenerar.php --gestor=.`, exatamente como faz o `CssAuditCommand.php`.

3. **Resolução de Tailwind e NODE_PATH no Gestor Remoto**:
   - No ambiente do Gestor remoto (onde não há `node_modules` local), o `tailwind-recursos.php` precisa resolver o executável global do Tailwind (`tailwindcss`) ou respeitar `NODE_PATH` (como `/opt/node-v22.22.3-linux-x64/lib/node_modules`) para resolver `@import "tailwindcss/utilities.css"` sem abortar.
   - O comando remoto de regeneração de CSS deve incluir a variável de ambiente `NODE_PATH` caso existente ou usar o resolvedor do sistema.

4. **Compreensão do Cache de Recursos do Projeto Privado**:
   - Validar que a etapa 3/8 (`project:sync-resources`) mantém o manifesto `.tailwind-build-manifest.json` com os 34 recursos do projeto em cache (0 a compilar, tempo de execução < 1s nas execuções subsequentes).

## 2. Escopo Técnico da Entrega

### 2.1 Extensão VS Code (`vscode-extension/`):
- Em `src/vmDiagnosticsPolicy.ts`:
  * No método `buildVmLogCommand(connection, logName)`: adicionar `sudo` na chamada remota:
    ```typescript
    return `ssh -o BatchMode=yes -o ConnectTimeout=15 -p ${normalized.port} "${normalized.user}@${normalized.host}" "sudo tail -n 100 -- '${remoteLog}'"`;
    ```
  * Atualizar os testes unitários de `vmDiagnosticsPolicy.test.cjs` para validar a presença do prefixo `sudo`.

### 2.2 Core CLI (`conn2flow/cli/` e arquitetura):
- Em `cli/src/Commands/CssRebuildCommand.php`:
  * Em `regenerarViaSsh()`: em vez de assumir `./c2f`, estruturar a invocação para chamar o script PHP canônico da instalação remota:
    ```php
    $argv = [
        'php',
        'controladores/agents/arquitetura/css-regenerar.php',
        '--gestor=.',
    ];
    ```
  * Se o comando remoto suportar `NODE_PATH`, repassar ou prefixar com a detecção de módulos globais de Node caso não haja `node_modules` local.
- Em `gestor/controladores/agents/arquitetura/tailwind-recursos.php`:
  * Em `tailwind_recursos_resolver_command()`: caso `$localCandidates` esteja vazio, verificar se existe o binário `tailwindcss` acessível no `PATH` do sistema antes de falhar.
- Em `tests/Unit/PHP/ProjectSshPublicPathReq050Test.php`:
  * Corrigir as asserções de escape de comando SSH (`testComandoRemotoEntraNaRaizDoGestorEEhCitadoArgumentoAArgumento`, `testValorHostilNoComandoRemotoNaoEscapaDaCitacao`, `testRunAsValidoEntraComoSudoCitado` e `testDiretorioRemotoEhCriadoAntesDoPrimeiroEnvio`) para serem portáveis entre Windows e Linux (Ubuntu CI).
  * No Linux/Ubuntu CI, o `escapeshellarg()` do PHP escapa aspas internas como `'\''`, o que fazia o workflow do GitHub Actions falhar na release.
