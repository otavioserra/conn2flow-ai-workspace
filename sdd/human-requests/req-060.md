## 1. Justificativa e Diagnóstico Técnico

O ciclo de desenvolvimento do subsistema de e-commerce (`conn2flow-site` REQ-058 a REQ-061) e as melhorias correspondentes no Core (`conn2flow` req-190/191) geraram um acervo substancial de evidências operacionais, técnicas defensivas e novos padrões arquiteturais documentados no relatório técnico [APRENDIZADOS-PARA-SKILLS-ECOMMERCE-2026-09-28.md](file:///C:/Users/otavi/OneDrive/Documentos/GIT/conn2flow-site/sdd/reports/APRENDIZADOS-PARA-SKILLS-ECOMMERCE-2026-09-28.md).

Uma varredura no catálogo atual de 40 skills canônicas revelou lacunas críticas de cobertura:
1. Nenhuma skill documentava a pegadinha de sessões em páginas públicas (`without_permission: true`), onde a chamada incondicional a cookies pode redirecionar visitantes para rotas de verificação.
2. Não havia orientação explícita sobre a injeção de scripts no `<head>` via `gestor_pagina_javascript_incluir()`, que quebra listeners diretos se executados antes do `DOMContentLoaded`.
3. As diretrizes do painel Tailwind não delimitavam com precisão o que possui variantes prontas (inclusão, edição, modais, botões) versus o que permanece Fomantic (listagens - BL-026).
4. O build Tailwind falhava silenciosamente em classes geradas dinamicamente em PHP/JS/JSON pela falta do registro formal de `tailwind_sources` e `tailwind_sources_reason`.
5. Renumerações de migrações Phinx causavam falhas repetidas no pipeline por ausência de rotina de limpeza de arquivos órfãos no destino.
6. A manipulação de arquivos JSON de módulos por scripts Python quebrava escapes nativos de barra (`\/`), gerando ruídos massivos de Git diff.
7. O sitemap e as rotas públicas não tinham regras normatizadas de exclusão automática para desfechos transacionais e fluxos de checkout.
8. O pipeline de deploy via API sofria gargalos de memória em tabelas volumosas (`paginas`) sem diagnóstico documentado no `php-error.log`.
9. Não existia um guia para execução de testes E2E com gateways de pagamento em ambientes remotos restritos (somente-leitura via SSH/SCP).
10. Não havia uma skill canônica dedicada para **gateways de pagamento seguros**, consolidando os padrões de prova de posse, tokens HMAC, idempotência de webhooks e dublês de teste.
11. Faltava um checklist formal para o auditor de qualidade (`c2f-reviewer-agent`) ao integrar módulos desenvolvidos por agentes táticos concorrentes.

Esta requisição formaliza a cristalização de todos os 13 aprendizados em **11 skills canônicas existentes** e a **criação de 1 nova skill canônica (`c2f-payment-gateways`)**, expandindo o ecossistema para **41 skills canônicas** sincronizadas em todos os 25 kits dos 5 repositórios.

## 2. Especificação Detalhada das Alterações

### 2.1 Atualização de 11 Skills Canônicas Existentes

#### 1. `c2f-gestor-functions`:
- **Regra de Sessão em Páginas Públicas**: Em páginas marcadas com `without_permission: true`, o `gestor.php` não executa `gestor_permissao()`, fazendo com que `gestor_usuario()` retorne vazio mesmo para compradores autenticados.
- **Diretriz Normativa**: Para identificar o usuário logado em páginas públicas, deve-se chamar `gestor_permissao_token()`, **mas estritamente sob a condição de que o cookie de autenticação exista** (`isset($_COOKIE[$_CONFIG['cookie-authname']])`). Sem essa checagem, a função `gestor_cookie_verificacao()` pode disparar um redirecionamento forçado do visitante anônimo para `_gestor-cookie-verify`.
- **Referência canônica**: Função `ecommerce_current_user()` da biblioteca de e-commerce.

#### 2. `c2f-javascript-ajax`:
- **Injeção de Scripts no `<head>`**: A função PHP `gestor_pagina_javascript_incluir()` injeta os scripts dos módulos no elemento `<head>` da página HTML.
- **Diretriz Normativa**: É proibido realizar consultas diretas ao DOM (ex: `document.getElementById('form')`) na raiz do arquivo JS, pois o DOM ainda não foi parseado, retornando `null` e causando o envio nativo sem interceptação AJAX.
- **Contrato**: Todo binding direto de eventos deve ser encapsulado em listener de `DOMContentLoaded` (ou `$(document).ready()`). Sempre dar preferência a **delegação de eventos** no objeto `document` (ex: `document.addEventListener('click', function(e) { if (e.target.matches(...)) ... })`).

#### 3. `c2f-interface-v2-architecture` e `c2f-tailwind-css-architecture`:
- **Variantes Tailwind no Painel Administrativo**: Com a ativação de `layout-administrativo-tailwind` e `framework_css: tailwindcss`, o mecanismo `interface_componente_variante()` fornece variantes `-tailwind` para: formulários de edição, **inclusão** (novo), modais (carregando, confirmação de deleção, alertas) e **botões de cabeçalho/rodapé** (`interface_botoes_html`, com ícones Lucide).
- **Restrição Vigente**: A página de **listagem de registros permanece no layout Fomantic** (`layout-administrativo-do-gestor`) até a implementação do item de backlog BL-026.
- **Armadilhas de Componente**: O botão de exclusão em Tailwind exige a inclusão do script `gestor/assets/interface/interface-tailwind.js` (escutando `.excluir[data-href]` e injetando token CSRF na confirmação). A chave `tooltip` ausente no array `$botoes` deve ser inicializada para evitar warnings de PHP.

#### 4. `c2f-tailwind-css-architecture`:
- **Classes Utilitárias Geradas Fora do HTML**: O compilador prévio de Tailwind analisa unicamente o HTML estático do recurso. Classes utilitárias montadas dinamicamente em PHP (ex: badges de status), manipuladas em JS (`classList.toggle('hidden')`) ou configuradas em JSON de módulos não entram no bundle gerado.
- **Diretriz Normativa**:
  - Em páginas do gestor/site: declarar o metadado `tailwind_sources` contendo o caminho relativo ao arquivo de origem (ex: `"../../../../products.php"`) **e** o campo obrigatório `tailwind_sources_reason` justificando a inclusão (o build acusa erro fatal se a razão for omitida).
  - Em bibliotecas do core: encapsular a paleta dinâmica num elemento `<template data-...>` inerte no próprio componente HTML para ser capturado pelo scanner.

#### 5. `c2f-database-operations` e `c2f-project-pipeline-and-tasks`:
- **Limpeza de Migrações Phinx Renumeradas**: A sincronização de arquivos do pipeline (`project:update-all`) opera em modo aditivo e não remove arquivos ausentes na origem.
- **Diretriz Normativa**: Ao renumerar uma migração Phinx para resolver conflito de timestamp com outro agente, o arquivo com o nome antigo DEVE ser removido manualmente do diretório de destino (`gestor/db/migrations/` no ambiente remoto ou espelho) antes de rodar o pipeline, caso contrário o Phinx aborta com erro fatal `Duplicate migration ... has the same version`.
- Em colisões entre agentes, a regra de desempate determina renumerar a própria migração para um timestamp mais recente.

#### 6. `c2f-json-resources-sync` e `c2f-shell-and-windows-traps`:
- **Preservação de Barras Escapadas (`\/`) em JSON de Módulos**: O PHP serializa JSON de módulos com escape de barra por padrão (`"products\/add\/"`).
- **Diretriz Normativa**: Ao ler e reescrever arquivos JSON de módulos via Python, deve-se obrigatoriamente manter o escape (`s.replace('/', '\\/')` quando presente no original), além de configurar `ensure_ascii=False` e preservar as quebras de linha nativas (LF/CRLF), impedindo que o Git diff aponte alterações artificiais em todo o arquivo.

#### 7. `c2f-project-pipeline-and-tasks`:
- **Expurgo de Registros Órfãos no Deploy (Lista `deletar`)**: O pipeline de banco de dados não exclui linhas omitidas nas fontes JSON.
- **Diretriz Normativa**: Para remover páginas, blocos ou metadados obsoletos no deploy, deve-se registrar explicitamente as chaves naturais no arquivo `project_tables_config.json` em `tabelas.<tabela>.deletar` (ex: `paginas`: `language, modulo, id`; `publisher_pages`: `language, page_id`).
- **Páginas Semente**: Para páginas de template que geram instâncias filhas (ex: semente de produto `store/<id>/`), remover a propriedade `without_permission` da semente para que apenas as páginas filhas públicas constem no sitemap.

#### 8. `c2f-projects-system`:
- **Regras de Indexação do Sitemap**: O gerador `sitemap.php` inclui automaticamente todas as páginas ativas que possuam `sem_permissao = 1`, filtradas por `sitemap_caminho_nao_indexavel()`.
- **Diretriz Normativa**: Ficam sumariamente excluídas do sitemap as rotas de desfecho transacional (`success`, `error`, `cancel`, `cancelled`, `confirmation`), sufixos de etapa (`.../payment`, `.../checkout`, `.../download`) e rotas do fluxo de compra (`cart`, `checkout`, `*-checkout`).
- Para retirar uma página específica do sitemap, deve-se desmarcar `sem_permissao` ou aplicar um desses sufixos padronizados. Validação obrigatória pós-deploy via `curl -s <url>/sitemap.xml`.

#### 9. `c2f-project-pipeline-and-tasks`:
- **Diagnóstico de Estouro de Memória no Deploy via API**: O endpoint `/_api/project/update` executa a sincronização de banco com `SELECT *` e `fetchAll`. Em projetos com centenas de páginas, pode ocorrer estouro do `memory_limit` padrão de 128 MB (gerando HTTP 500 sem corpo descritivo).
- **Diretriz Normativa**: Diante de HTTP 500 no deploy, inspecionar imediatamente o arquivo `conn2flow-gestor/logs/php-error.log` no servidor de destino. O endpoint do Core foi ajustado para invocar `api_memoria_minima('1024M')`.

#### 10. `c2f-documentation-governance`:
- **Fluxo Mandatório Pós-Alteração de Código (`docs:audit`)**: Modificar qualquer arquivo de código listado no cabeçalho `sources:` de um documento normativo invalida o campo `verified_at`, gerando avisos de fonte divergente.
- **Diretriz Normativa**: Após concluir alterações em código, o executor deve:
  1. Executar `c2f docs:audit` para listar as documentações afetadas.
  2. Atualizar o conteúdo textual das documentações que descrevem as funções ou comportamentos alterados.
  3. Atualizar o metadado `verified_at` com o hash do novo commit.
  4. Executar `c2f docs:extract <biblioteca>` se novas funções foram adicionadas à API.
  5. Compilar as docs para publicação com `./c2f docs:build --project=<id>`.

#### 11. `c2f-agent-visual-inspection`:
- **Roteiro de Validação E2E sem Acesso de Escrita Remota**: Em ambientes de homologação/Lab onde o agente possui credenciais de leitura de logs mas não permissão de escrita via SSH/SCP:
  1. Extrair a sessão administrativa com `./c2f auth:cookie --project=<id>` para o jar Netscape em `temp/agent-cookies.txt` e injetar no Playwright via `context.addCookies`.
  2. Isolar contextos de navegação: contexto limpo para visitante anônimo e contexto com cookies para comprador autenticado.
  3. Preenchimento de componentes seguros em iframes (ex: Stripe Payment Element) através de `page.frameLocator('#checkout-payment-element iframe').first()`, preenchendo cartão de teste após aguardar o estado habilitado do formulário.
  4. Interceptar caixas de diálogo nativas do navegador via `page.on('dialog', d => d.accept())`.
  5. Auditoria de banco por interface administrativa: inspecionar telas de detalhe do pedido para validar status e histórico de transações.
  6. Teste de webhooks com injeção HTTP direta: disparar requisições POST com payloads autênticos do gateway diretamente no endpoint e atestar idempotência na tela do pedido.
  7. Auditoria de tráfego de rede via `page.on('request')` para certificar que SDKs externos (ex: PayPal) não são carregados quando o gateway não foi selecionado.
  8. Sanitização de saída de console para evitar vazamento de credenciais e cookies sensíveis.

#### 12. `c2f-reviewer-agent`:
- **Checklist de Auditoria para Integração de Módulos Concorrentes**:
  - Validar se endpoints públicos utilizam o padrão correto e não funções administrativas (`interface_ajax_*`).
  - Auditar rate limiting por IP (`gestor_sessao_delimitador`) e obrigatoriedade de aceite de termos de uso em formulários que criam contas ou registros.
  - Impedir a criação anti-padrão de múltiplas linhas na tabela `paginas` por entidade do usuário (detalhes devem ser página única com parâmetro).
  - Bloquear vinculação de recursos a endereços de e-mail sem verificação prévia de posse.
  - Checar consistência dos frameworks de estilo (proibindo classes não compiladas).
  - Executar `php -l` e busca por `function <nome>(` para prevenir colisões de funções redeclaradas ao mesclar branches.

### 2.2 Criação da Nova Skill Canônica: `c2f-payment-gateways`

Deverá ser criada a skill `c2f-payment-gateways/SKILL.md` contendo as seguintes diretrizes arquiteturais para gateways de pagamento (Stripe, PayPal, etc.):

1. **Autoridade Estrita do Servidor**: Preço unitário, moeda, descontos e taxas são definidos e validados exclusivamente no backend. O cliente frontend trafega apenas identificadores e quantidades.
2. **Tokens de Pedido Criptográficos HMAC**: Acesso público ao pedido por link externo protegido por HMAC (`HMAC(OPENSSL_PASSWORD, numero|salt)`), persistindo unicamente o salt no banco de dados.
3. **Prova de Posse em Verificações de Estado**: O estado do pagamento é lido diretamente da API oficial do gateway com prova de posse obrigatória: conferência do identificador do pedido nos metadados (`metadata` / `custom_id`), correspondência exata do valor cobrado e da moeda.
4. **Captura Mandatória no Backend**: Para gateways como PayPal, o cliente no navegador apenas autoriza a ordem; a captura financeira efetiva deve ocorrer exclusivamente no servidor.
5. **Webhooks Minimalistas e Idempotentes**: O webhook atua primariamente como sinalizador, identificando o pedido e disparando a ressincronização via API oficial. Cada evento de gateway é registrado com seu identificador único (`gateway_event_id`) para garantir idempotência absoluta diante de retentativas.
6. **Carregamento Condicional de SDKs**: SDKs de terceiros pesados no frontend só devem ser baixados quando o pedido especificamente selecionar aquele método de pagamento.
7. **Gateway Padrão (Fallback Seguro)**: Na ausência de seleção explícita pelo comprador, o sistema deve assumir o gateway padrão do lojista (ex: Stripe).
8. **Testes Unitários sem Credenciais**: Estratégia de testes de checkout baseada em dublês/mocks das funções da biblioteca do gateway, permitindo validação automatizada em pipelines de CI sem credenciais reais.
